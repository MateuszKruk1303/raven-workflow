Raven / mapa decyzji / stan 15.10.2026

Trzy wejścia.
Wspólna metoda pracy.

Od pomysłu do pilota, przez zmianę w istniejącej aplikacji, po osobistą pracę z ticketami Jiry w zespole enterprise.

Stan skilli i uzgodnień, nie certyfikat gotowości aplikacji. „Istnieje” oznacza zapisany skill; pełny workflow nie został jeszcze sprawdzony na rzeczywistym change od początku do końca.

02 / Od wymagania do zweryfikowanej zmiany

Metoda jest wspólna, artefakty wykonania są w GitHubie. Import Jiry ma już osobny skill; lokalny adapter pozostaje propozycją. raven-workflow jest przewodnikiem i routerem — nie etapem wykonania.

01 →

Plan + review

Wymagania, kontrakty, ryzyka i scenariusze testowe. Po review akceptacja lub poprawki zlecone przez Ciebie.

raven-plan → raven-plan-review
02 →

Implementacja + review

Realizacja faz i ich bramek. Osobno wywołujesz techniczne review; Ty wybierasz poprawki.

raven-implement → raven-implement-review
03 →

Twój odbiór

Sprawdzasz aplikację i zgłaszasz problemy. Poprawki wracają do implementacji oraz odpowiedniej weryfikacji. Bez automatycznego startu testów lub PR.

Decyzja człowieka
04 →

Trwałe testy + review

Dobór unit/integration/E2E do ryzyka. Pisanie i uruchomienie testów, potem osobne niezależne review i Twoje decyzje.

raven-test → raven-test-review

Tryby można mieszać. Świeży reviewer testów czyta te same wersje źródeł co autor, bez jego transkryptu. Auto naprawia wady testów w ustalonym zakresie; błąd produktu lub rozbieżność wymagań wraca do użytkownika. Limity prób zapobiegają nieskończonym pętlom.

Brownfield: testy przed zmianą — dostępne. Po akceptacji planu, przed ryzykownym refaktorem: raven-test → raven-test-review albo raven-auto-test w trybie before-change. Zabezpiecz uzgodnione zachowanie bazowej wersji. Dla bugfixu reprodukcja może kończyć się oczekiwanym RED; nie jest to PASS produktu.
Plan → testy przed zmianą + review → implementacja → odbiór → końcowe testy + review. Po zmianie ponownie sprawdź zabezpieczenia na finalnym SHA; nie pisz tych samych testów drugi raz.
↓ raven-pr: opis zmian, powiązania, kompromisy → checki CI → review zespołu, jeśli wymagane → merge ↓

raven-pr nie audytuje gotowości i nie uruchamia testów. Obowiązkowy etap testów jest regułą metody. Checki i blokady merge wynikają z konfiguracji repo. W aktualnym GH flow Done dopiero po merge; w wariancie Jira nie oznacza to automatycznej zmiany statusu biznesowego ticketu.

03 / Co oznacza „dostarczone”?

Zmiana w istniejącym produkcie

Przekazanie do procesu zespołu

PR i dowody, wymagane review, CI, merge i wydanie według zasad projektu. Agent nie przejmuje uprawnień do deploya ani decyzji o zamknięciu Jiry.

Greenfield: luka między merge a pilotem

Wypuszczenie pilota

Potrzebne są decyzje o środowisku, konfiguracji, danych/migracjach, sposobie udostępnienia, diagnostyce i wycofaniu zmiany oraz sprawdzenie po wydaniu.

Brak obecnie dedykowanego procesu Raven release/deploy. Dla pilota lokalnego wystarczy odpowiedni zakres instalacji i uruchomienia; nie zakładamy hostingu dla każdego produktu.

04 / Dwa miejsca, różne odpowiedzialności

Jira definiuje zadanie. GitHub przechowuje wykonanie agentowe. To ma być podział odpowiedzialności, bez dwóch niezależnych wersji wymagań.

Kontrakt raven-jira-roadmap — skill istnieje
  1. Wejście: jawna lista kluczy/URL-i ticketów, sprint albo epika; pokaż znaleziony zakres, paginację i wyłączenia.
  2. Odczytaj wymagania, istotne ludzkie ustalenia, zależności i dostępne kryteria. Niejasności kieruj do użytkownika; komentarz nie nadpisuje automatycznie każdego wcześniejszego ustalenia.
  3. Domyślnie wykonywalny ticket Jiry → change Raven; techniczne fazy/taski powstają podczas planowania. Dla epiki/sprintu importuj wybrane tickety. Podział jednego ticketu na wiele changes wymaga jawnego mapowania.
  4. Zapisz trwałe mapowanie źródło → obiekty GH i wersję wejścia. Ponowienie aktualizuje istniejące obiekty, bez duplikatów lub kasowania rozpoczętej pracy.
  5. Po zmianie Jiry pokaż różnice i wpływ na plan/aktywną pracę. Nie uruchamiaj nieustalonej automatycznej synchronizacji zwrotnej.
  6. Zatrzymaj się na kolejce gotowej do planowania. Import sprintu nie jest zgodą na implementację wszystkich ticketów.

Skill zapisany i zwalidowany strukturalnie; import rzeczywistego sprintu nie został jeszcze sprawdzony.

Współpraca dwóch devów: zasady i ograniczenia

Jawne przypisanie właściciela aktywnego taska, osobne branche/worktree, checkpointy przekazania i kontrola równoczesnych zapisów. Jeden task nie powinien mieć dwóch nieświadomych siebie wykonawców. Obecny kontrakt GH ma odczyt przed zapisem i ochronę przed duplikatami, ale nie pełny mechanizm koordynacji kilku devów.

Prywatność musi obejmować repo przechowujące issues i raporty oraz powiązane artefakty, nie tylko Project. Setup powinien sprawdzić rzeczywiste dostępy i zasady firmowej organizacji. Sam diagram nie konfiguruje uprawnień.

Alternatywa: lokalny, ignorowany katalog

Gdy przestrzeń GH na artefakty nie jest dostępna lub pożądana: proponowany adapter .raven/changes/PROJ-123/ przechowuje snapshot, plan, review i postęp. Jira nadal definiuje wymagania, kod/testy trafiają normalnie do repo. Lokalne ignorowanie można ustawić poza współdzielonym .gitignore; trzeba też wykluczyć katalog z paczek i uploadów artefaktów.

Ten wariant utrudnia współpracę i przekazanie kontekstu. Git ignore chroni przed zwykłym dodaniem plików do Git, nie jest kontrolą dostępu ani zakazem wysyłania ich narzędziom. Adapter lokalny nie istnieje obecnie; wymaga zmiany dzisiejszej zasady „GH jako jedyny trwały kontekst change”.

06 / Ocena kierunku

Trzy scenariusze są spójne, jeśli oddzielimy metodę od miejsca przechowywania artefaktów. Nie potrzeba trzech zestawów implementatorów, testerów i reviewerów. Potrzeba różnych wejść, jednoznacznych źródeł wymagań i poprawnego przekazania pracy.

Obecne Raven najlepiej pokrywa wykonanie change’a w projekcie korzystającym z GH. Brownfield ma już narzędzia rozpoznania i zabezpieczenia zastanego kodu. Enterprise ma skill importu Jira → GH oraz kontrakt osobnego repo artefaktów; wymaga sprawdzenia integracji i konfiguracji w docelowej organizacji. Greenfield do pilota wymaga jeszcze domknięcia wydania.

Nie buduj pełnej synchronizacji dwukierunkowej Jiry i GitHuba na start. Obecny skill importuje wybrany zakres i na żądanie pokazuje różnice; nie zapisuje nic do Jiry. Dzięki temu odpowiedzialność za wymagania pozostaje czytelna.

Źródła: lokalne instrukcje raven-workflow, repo-map, frame, research, domain-distillation, rule-review, jira-roadmap i skilli plan/implement/test/PR oraz kontrakty GitHub i before-change; materiały 10x „legacy & large scale” (mapowanie repo, refaktoryzacja, domena); ustalenia tej rozmowy. Raven Pilot jest deprecated — jego skille nie są częścią obecnej ścieżki do pilota.

Dokument samodzielny: działa offline, bez zewnętrznych bibliotek, fontów i telemetrii. Przyciski zmieniają widok, nie uruchamiają skilli ani nie modyfikują projektu.
