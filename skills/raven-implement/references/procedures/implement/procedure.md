# Implementacja i testy

Przed zależną implementacją sprawdź również aktualne niezależne `plan-review.md` dla bieżącego fingerprintu i rozstrzygnięcie blokujących findings. Sama akceptacja planu nie zastępuje zachowanego etapu review; brak lub nieaktualne review kieruje do raven-plan-review/auto-plan. Nie wymagaj nowego review dla samych checkboxów lub checkpointu.

Stosuj [kontrakt pracy](../../../../raven-workflow/references/change-contract.md), [dyscyplinę](references/implementation-discipline.md) i [postęp](references/progress-format.md). Przeczytaj cały obowiązujący kontrakt, istotne instrukcje/lessons oraz kod dotkniętych obszarów. Nie odczytuj wszystkich historycznych raportów.

1. Utwórz albo odzyskaj osobny worktree i branch change przed edycją; wykorzystaj istniejące powiązanie przy wznowieniu. Nie zagnieżdżaj worktree ani nie usuwaj cudzej pracy. Sprawdź fingerprint, rzeczywistą zgodę, bazę/HEAD, branch/worktree, staging i dirty state. Ustal bazę przed edycją, nie resetuj cudzej pracy. Przy wznowieniu zachowaj bazę i ukończone kroki z aktualnymi dowodami. Bez Git zgłoś brak przed zależnym cyklem commitów/review; nie publikuj repo po cichu.
2. Wykonuj pozostałe kroki kontraktu wraz z odpowiednimi testami. Istniejące wzorce mają pierwszeństwo przed nową abstrakcją. Nie dodawaj niepotrzebnych runnerów/warstw. Dla E2E czytaj [setup](../../../../raven-test/references/procedures/e2e-setup/procedure.md) i [wykonanie](../../../../raven-test/references/procedures/e2e/procedure.md), tylko gdy wybrano tę warstwę.
3. Rozbieżność Minor to szczegół mieszczący się w kontrakcie: rozstrzygnij i zapisz. Structural zmienia gwarancję, wymaganie lub zatwierdzoną istotną decyzję: pokaż wpływ i wróć do akceptacji zmienionego kontraktu przed zależną pracą. Nie nazywaj rozszerzenia zakresu rutynową naprawą.
4. Uruchom wymagane kontrole projektu i planu. Wynik musi dotyczyć rzeczywistego drzewa, konfiguracji i środowiska. Rozróżniaj defekt produktu, testu i środowiska. Naprawiaj w zakresie; po dwóch nieskutecznych próbach jednego problemu zapisz blokadę i reprodukcję. Nie osłabiaj asercji ani bramek dla zielonego wyniku.
5. Przejrzyj diff i celowo stage'uj własne pliki, w tym należące do change dokumenty. Nie używaj ślepego `git add .` ani nie przejmuj istniejącego stagingu. Lokalne commity w zleconym zakresie nie potrzebują osobnej akceptacji komunikatu; respektuj odmienne jawne polecenie użytkownika. Nie commituj sekretów, tymczasowych logów ani stanu auth.
6. Aktualizuj Progress i checkpoint poza kontraktem. Wcześnie publikuj/aktualizuj draft tylko zgodnie z autoryzowaną polityką; offline pracuj lokalnie. Zapisz zakres, testy, istotne decyzje, nierozwiązane bramki i next. Nie dopisuj fikcyjnego odbioru człowieka.
7. Oddaj stabilne drzewo do jednego niezależnego review wymagań, kodu i testów. Nie pozostawiaj procesu, który nadal zmienia oceniany kod. Dodatkowy tester wynika z ryzyka. Odbiór użytkownika i wymagane CI poprzedzają osobno autoryzowany merge; nie ma obowiązkowej późnej fazy pisania testów.
